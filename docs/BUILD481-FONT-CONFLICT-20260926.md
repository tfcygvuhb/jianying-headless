# 原始 STIX Regular 字体的相互冲突证据

2026-09-24 的隔离负例使用原始 STIX General Regular OTF（SHA-256 前缀 `5add3f3f`），剪映 GUI 保存后将文字材料与样式的字体路径改为应用 `SystemFont/zh-hans.ttf`，严格绑定回读失败。2026-09-25 的另一份隔离工程使用**相同字体字节**，三轮 GUI 保存、正常退出、冷启动与回读均保留草稿内该字体路径，四镜像与源素材哈希一致。两组应用可见 version/build、Team ID、动态库和 codec 指纹相同；旧组没有完整主程序文件哈希或字体缓存快照。两组输入文案和字号不同：旧组为 `STIX GENERAL 123` / 42，新组为 `STIX 123` / 12。完整只读差异审计在 `work/build481-font-readonly-audit-20260926/REPORT.md` 和 `audit.json`。

这证明“该字节的草稿字体路径在 GUI 保存时**必定**丢失”不是当前可支持的普遍结论，也不证明新组真实画面使用了 STIX 字形。新组的截图未选中文字、未显示剪映字体面板中的字体身份；既有视觉比较缺少同文案同字号的 SystemFont 负对照和预定阈值。字段保留、衬线外观与单次原生导出均不足以开放任意字体或此原始 SHA。

下一步必须在已解锁的同一会话，用旧、新文案与字号各自建立原始 STIX / SystemFont 配对的隔离工程，交错运行至少三轮。每轮选中文字并通过 Accessibility 回读字体面板，保存、完全退出、冷重开后再次读 UI 身份、材料与样式路径、文件 SHA，按同帧同裁切和预定阈值比较画面。若 UI 身份无法可靠读取或 A/B 画面不能区分，继续报告为 `INCONCLUSIVE`。当前正式字体白名单和失败关闭门禁不变。
