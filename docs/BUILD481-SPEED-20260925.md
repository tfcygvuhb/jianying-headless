## 2× 与连续区间的边界

11 个倍率的离线 `build`/`verify-build` 均通过，但这只证明草稿字段可写。
2× 的 2 秒目标在源入点 0 与 0.5 秒时均输出 60/60 帧；3 秒目标在源入点
0 时输出 **89/90 帧**，源入点 0.5 秒时输出 90/90 帧。四格输出均可解码，
问题出在一格缺失末帧；不能以进程成功或可解码代替完整帧数验收。
源帧率和时间戳精确，理论末帧存在，目前没有已验证的安全修复。
2× 和其余未逐项验收的倍率仍被正式导出门禁拒绝；不能把六个离散点
推广为连续 0.1–8 倍范围。矩阵数据位于
`work/build481-speed-range-20260924/matrix-2x2-20260925/matrix-evidence.json`。

同一 3 秒、零入点 2× 草稿又在剪映官方 GUI 完成保存冷重开和原生导出。
GUI 输出为 90/90 帧，末帧正确显示源 frame 0178；容器品牌为 `qt  `，
不能当作标准 MP4 `isom` 证据。此结果表明 89/90 缺帧没有在 GUI 路径复现。
只在 work-only C++ 副本把原生 writer selector `0x279` 从 1 改为 0，
得到 90/90 帧和 `qt  ` 品牌，但末帧显示源 frame 0177，仍与 GUI 不同。
改写 writer 既未得到标准 MP4，也未复现正确末帧，因此正式源码与 2× 门禁不变。
GUI 与 work-only 对照分别记录在
`work/build481-speed-range-20260924/rate-2p0/gui-official-export-20260925/evidence.md`
和 `work/build481-speed-range-20260924/rate-2p0/helper-export-writer0-20260925/evidence.md`。

后续 work-only 对照解密了剪映保存后的 GUI 草稿：源起点/时长、目标起点/时长
与 helper 都是 `0/6,000,000 → 0/3,000,000 µs`、`2×`，未找到实质时间范围差异。
在 writer1 下同步增加目标 1、2、3 µs（源分别增加 2、4、6 µs）均变成
91 帧、3.033332 秒，超出目标；writer0 加 1 µs 源入点可得到 90 帧且
末源帧与 GUI 一致，但输出仍是 `qt  `，并改变了原定零入点。
这些候选都不满足正式 MP4 与精确时间范围要求，因此 2× 继续关闭。
